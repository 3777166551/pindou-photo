## ⭐ 2026-08-30 落地验证更新(已集成进 APK,本节为实测结论,优先阅读)

针对用户反馈"油画感还是很重",按本文档路线 A 实测验证,**方案可行**:

| 候选 | 实测结论 |
|---|---|
| AnimeGANv3_JP_face(6.1MB) | **人脸真·二次元**(大眼/赛璐璐/描线),但**只能用于对齐后的人脸**,整图用会把场景洗白(实测 home/油画全毁);人脸区 parsenet 掩膜覆盖正常(0.28~0.46) |
| White-box Cartoonization PINTO #019(7.6MB) | **背景平涂去油画感的最大功臣**:固定 720×720 输入(NCHW /127.5-1)、输出 NHWC、tanh 输出会略超 [-1,1] 需 clamp;桌面单帧 ~0.9s;短边用边缘像素复制补齐再裁回 |
| AnimeGANv2_Paprika(8.6MB) | 更浓的饱和厚涂,**油画感反而更重**,弃用 |
| informative_drawings(17MB) | 单通道线稿,本轮未用 |
| 端侧 SD(路线 B) | 维持不用 |

**最终组合 = STYLE_ANIME2D「二次元平涂」按钮**:WBC 平涂底图 + YuNet/parsenet/GFPGAN 对齐复用 + JP_face 贴脸 + **Reinhard Lab 颜色迁移**(必须!否则深肤色被 JP_face 漂成苍白动漫皮,和额头/脖子衔接违和;迁移后 dE 32.6→1.1)。无人脸时自动=纯 WBC 卡通平涂,也是合适的场景兜底。

验证中另发现并修复**第二个隐蔽 bug**:人脸贴回包围盒 `mapCorners` 误用正变换矩阵(模板四角→原图应该用逆变换)。后果:系数<1 的大脸(特写/自拍)包围盒缩到图像原点,**脸部修复实际从未贴上**;系数>1 的小脸(合影)碰巧覆盖才"看起来能用"。已修(AnimeStyle.java + AppPath.java),Ghibli 管线的特写脸同步受益。

**2026-08-30 三次更新(v2.6,用户反馈"油画感仍重+脸诡异")**:复合贴脸的天生缺陷是"动漫脸贴写实头发/身体"的风格断裂。实测结论:JP_face **整图**风格化在自拍/特写上效果最佳(全图统一画风、无贴缝、零违和),但会把小脸抹成空白椭圆(face007 全家福四脸全毁)。最终 STYLE_ANIME2D 改为自适应分流:所有检测脸框高 ≥30% 图高且非黑白照 → JP_face 整图 + 全图 Reinhard 保色;有小脸/无人脸 → WBC 平涂 + 逐脸贴回(原路线)。另:WBC+色阶量化+Sobel 描线的"强化赛璐璐"后处理实测翻车(暗部糊成黑块),弃用。

**2026-08-30 四次更新(去油画感冲刺,接力点)**:用户确认二次元平涂方向正确但油画感仍重。定位:剩余油画感 = WBC/JP_face 输出内部的连续渐变(笔触)。**验证成功的赛璐璐后处理配方**(py_cel2.py,效果 cel2_out\):双边滤波×2 → RGB k-means 色阶量化(风景 k=24~36 / 人像 k=48)→ 细描线(取自风格化输出自身的 Laplacian,1px,30~40% 透明度;**线绝不能取自原图**)。v1 翻车原因已明:k 太少 + 原图粗黑线。待修:纹理区量化斑点需小连通域清理。集成计划与参数见 HANDOFF.md §2.5,下一会话从此接手,完成后升 v2.7。

**2026-08-30 五次更新(v2.7,油画感收尾,已集成进 APK)**:上一行计划已全部落地,并实测了用户思路「**先把人的表情二次元化,再转换**」——特写路线改为两段式:JP_face 整图先二次元化 → WBC 二次平涂压笔触(py_twostage 对照实验完胜单段,输出 twostage_out\),再接赛璐璐后处理 `celPost`(全 Java,双边 LUT 免 exp + k-means 32k 采样训练 + 多数票清斑 + 细描线)。本轮五条关键实测结论:
1. **描线源必须分路线**:人像取双边平滑图的 Laplacian(真边缘;取量化色块图会把眼睛切成黑块,py_cel4 隔离验证);风景/静物取量化色块图的 Laplacian(只在色块边界出线,橘皮/雕花墙纹理不再炸黑噪点,py_cel3)。
2. **量化分配必须在原分辨率逐像素做**:512 缩图量化+最近邻上采样会把合影小脸五官抹成空洞(face007 教训);训练可在 512 缩图(性能),与 py_twostage D/H 全分辨率配方对齐。
3. **Reinhard 升级为框统计羽化混合**:纯全图统计在特写构图下被背景/服装稀释,深肤色脸的蓝黑偏色修不动;纯框统计全局应用又把背景漂白。框内用脸框并集统计、框外用全图统计、距离线性羽化;两个映射都是 Lab 线性变换,先混 scale/off 再单次 Lab 往返,零额外开销。
4. **深肤色青蓝阴影需阴影暖化**:Lab 上 a*/b* 双负的残聚类,均值/方差映射修不掉;框内 L<50 且 b*>-12 的阴影像素 a*→+5、b*→+2 按羽化权重软混合有效(face001 显著改善;b*>-12 守卫排除饱和蓝物体——皮肤蓝阴影 b*≈-5 vs 藏青衣物 b*≈-20,分离度好)。**大坑:Python cv2 的 Lab a/b 以 128 为中心、Java ColorMath 以 0 为中心**——Python 判"负 b*"必须先减 128,本轮照抄 Java 写法在 Python 跑了一整轮无效实验才发现。
5. v2.7 桌面回归(anime2d_v3\,8 图 × 三路线 + 黑白守卫)全过;桌面 1024² 全管线 4~5s(其中 celPost <1s),合影 4 脸 19.5s。遗留:face001 眼周(L≥50)仍有少量蓝晕,深肤色修到"可用"未到"完美"。

**2026-08-30 六次更新(v2.8,换路线:JP_face 路线整体废弃)**:用户实测 v2.7 反馈"**油画感还是太重 + 表情很不对,也许这条路走不通**",全面换思路。新结论:JP_face 类"整图动漫化"路线的两大缺陷是**天生**的——①输出内部的连续渐变(笔触感)怎么量化都像"色块化照片"而非动漫;②模型自带的动漫表情是木偶脸(呆滞大眼),与真人的表情对不上。**新路线 = WBC 平涂色块 × PortraitSketch 真人线稿(钢笔淡彩插画)**,表情线条直接取自真人原照片(表情永远正确),平涂+粗墨线才是动漫的真正视觉语言(油画感根除)。配方(route3~route6 七轮实验):
1. **线稿源对比**:informative_drawings(17MB)细腻但乏力;PortraitSketch(4MB,已在包内复用!)浓墨有力但皱纹脸会糊满墨线、风景/物体糊成黑团——用**形态学开运算(7×7 椭圆)**删细笔划(皱纹/织物 1~3px 被删,五官粗轮廓保留)解决皱纹问题;风景仍走 v2.7 的量化色块描线。
2. **合成方式**:乘法(色块 × 线稿亮度^0.85,floor 0.25)优于 alpha 叠加(后者对阈值敏感,易全图压黑)。
3. **收益**:合影不再逐脸贴回(2.5s vs 19.5s);深肤色天然正确(WBC 直接保原色,无 JP 漂白环节);黑白照天然灰度墨绘;APK 反而减小(JP_face 6.1MB 移除,无新增模型)。
4. **实验记录**:route2(线稿极性搞反全图压黑)、route3(乘法胜出)、route4(线稿源对比+风景适用性)、route5(强度曲线)、route6(开运算定案);cels 前代实验见 py_cel2~5。
5. 已知取舍:face001 类皱纹特写眼周仍有 Sketch 固有的墨块(模型对深肤色光影的画法);照片背景大面积深色植物可能被 Sketch 画成墨团(有人脸即走线稿路线);Disney/USA 等官方风格确认 Patreon 门禁无法下载(HF 亦无镜像)。

## ⭐ 最终结论(2026-08-30,十一次更新 v2.13:本地路线到顶,云端才是正解)

用户对 v2.12 JP 日漫路线仍不满意("看起来很奇怪")。**自我复检确认**:JP_face 把眨眼脸画成廉价简笔画脸、背景成破木板+乱线——这是 5MB 级本地 GAN 的能力天花板,不是管线问题。**本轮 v2.4→v2.12 共九轮本地修补(贴脸/平涂/量化/线稿合成/硬边界/自适应/JP日漫)全部到顶,每轮解决一个抱怨又暴露下一个**。

**换大路:云端扩散模型**(项目本就内置火山方舟 Seedream 5.0 图生图,商业 APP 全走此路)。实测 `py_cloud.py`:用户照片 + 手绘二次元提示词,**26.5 秒出 2K 专业手绘动漫**——大眼动漫脸/干净线条/柔和赛璐璐/笑容双马尾全保留/背景柔和简化,质量与本地差距是代差。提示词已验证:

> 把这张照片转成日系手绘二次元插画:少女漫画画风,干净的线条,柔和的赛璐璐上色,大眼睛动漫脸,保留人物的发型、服装、姿势和表情,背景简化成柔和的动漫背景,整体明亮清新

**v2.13 落地**:①「二次元平涂」按钮点击弹选择框——**云端 AI 手绘二次元(推荐,需网络约30秒)** / 本地离线转换(数秒,效果一般);②AI 标签页"二次元"预置词更新为上述验证词。本地三路线(v2.12)保留为离线兜底,不再继续投入。

**给后继者的建议**:不要再试图用本地小模型逼近云端质量——AnimeGANv3 系(4~8MB)的动漫脸渲染能力天花板清晰可见;若要离线高质量,唯一路是端侧扩散(SD-Turbo 级,1GB+,见路线 B),工程代价大;个人自用场景云端按量付费(单张 2K 约 ¥0.2)是最优解。

**2026-08-31 产品方向定案(v2.15)**:确认停止投入本地三转二,本地 AnimeGAN/WBC/YuNet/Parsenet 模型(约 55.6MB)已全部移出 APK(备份于 `backup_20260831\models\`,AnimeStyle.java 同),仅保留 u2netp 供一键去背景。现三条路:① 云端 Seedream「✨ 二次元」预设一站式直转(首选);② **外部图片 + 去水印**:用户用任何免费 AI 工具(PC 开源软件/网页版)做好二次元图存相册,APP 编辑页「照片预处理 → 🩹 去水印」拖框盖住水印,`WatermarkRemover` 掩码式修复(环带中值比对 + 洋葱剥皮 + 松弛,只修水印笔画不动背景;桌面 96 用例回归见 `tools\bgtest\wm\WatermarkSuite.java`,平均 PSNR 21.4→46.0dB);③ 云端 AI 标签页自定义提示词。

桌面验证工具:`AppPath.java mode=2d`(逐字复刻 APP 路径),输出 `tools\bgtest\anime2d_out\`;Python 对照实验 `py_style_try.py` / `py_hybrid.py`(注意 **cv2 5.0 的 warpAffine 语义与 4.x 相反**,正向/逆向映射写反会裁歪)。

工具链注意:cv2 5.0 warpAffine 改为正向映射语义(旧版 `dst(x,y)=src(M·(x,y))`)。

## 一、本地代码现状（已读代码确认）

| 项 | 现状 |
|---|---|
| 技术栈 | 纯 Java + 免 Gradle 构建链（`build_apk.bat` + `tools\`），零第三方框架 |
| 推理引擎 | ONNX Runtime **1.17.1**（`tools\ort_aar`，classes.jar + arm64-v8a 两个 .so） |
| AI 资产 | 共 **41.8MB**：animegan3_ghibli(6.7MB) / shinkai(4.2MB) / hayao(4.2MB) / parsing_parsenet_int8(21.6MB) / u2netp(4.5MB) / yunet(232KB) |
| 本地三转二 | `AnimeStyle.java`：Shinkai/Hayao 整图打底 → YuNet 人脸检测(5 关键点) → 相似变换对齐 512×512 → Ghibli 人像模型 → parsenet 语义掩膜贴回；带灰度守卫、检测阈值调优(0.40)、多脸上限(8) |
| 云端兜底 | `AiStyleClient.java`：火山方舟 Seedream 5.0 图生图，内置卡通/二次元/3D/乐高/极简预设 |
| 输出约束 | 拼豆图纸最多 116×116 格、≤120 色 → **风格化 512 分辨率完全够用，瓶颈在"像不像二次元"，不在分辨率** |

关键结论：`AnimeStyle.java` 的人脸管线（检测→对齐→风格化→掩膜贴回）**恰好就是 AnimeGANv3 官方人像推理的标准流程**，这意味着换/加官方同族模型几乎零改造。

## 二、市面 APP 的做法

### 主流 APP：全是云端推理

美图秀秀 AI 绘画、醒图、一甜相机、ToonMe、Voila AI Artist、Anime AI 等，

### 真正离线的产品：用的正是本项目这条路

- 结论：**本项目的本地路线与市面离线产品同源，方向正确**；提升点是"加风格"，而不是"换架构"

## 三、纯手机端三条技术路线

### 路线 A：轻量 GAN 小模型（本项目当前路线，5~30MB 级）

| 模型 | 特点 | 移动端现状 |
|---|---|---|
| **AnimeGANv3**（已用） | Double-Tail GAN，最轻；官方称 2.4MB tiny 模型在 iPhone14 上 512 输入可达 50FPS | ONNX/TFLite 直接跑 |
| **AnimeGANv2 face_paint_512_v2** | "动漫厚涂脸"风格，与 Ghibli 赛璐璐感差异明显，社区最火人像模型 | 现成 ONNX：akhaliq/AnimeGANv2-ONNX |
| **White-box Cartoonization** | CVPR2020，通用卡通化、泛化好，风格偏描线+平涂 | 现成 ONNX 在 PINTO model zoo #019；另有 TFLite 教程 |
| U-GAT-IT selfie2anime | 较老，训练集偏向女性脸 | 有 TFLite 教程，不推荐 |
| AnimeGANv3 人像风格全家桶 | Disney / USA / Kpop / Trump / Comic / Cute / 8bit / 油画 / Nordic myth(仅 2.4MB) 等 | 官方 releases 与 Portrait_Inference 仓库提供 ONNX |

### 路线 B：端侧扩散模型（真"精品二次元"，GB 级，**不建议本项目采用**）

| 方案 | 说明 | 代价 |
|---|---|---|
| MNN-Diffusion（阿里开源） | SD1.5/LCM 端侧跑文生图 | 模型 1~2GB 需单独下载；要集成 MNN C++ 运行时 |
| Qualcomm AI Hub w8a16 | SD1.5/v2.1 量化到骁龙 NPU | UNet 一项就 ~1.2GB；仅骁龙旗舰可用 |
| Local-Diffusion / stable-diffusion.cpp | CPU 量化推理移植 | 同样 GB 级、兼容性差 |

不采用的理由：
1. 体积与机型兼容性完全不适合打进 APK；
2. img2img + 少步数采样（LCM/Turbo）质量不稳；
3. 会破坏本项目纯 Java 免 Gradle 构建链；
4. "精品二次元"需求已有云端 Seedream 覆盖；
5. 拼豆输出 ≤120 色，扩散模型的高画质优势被归色环节抹掉大半。

### 路线 C：推理加速（不换模型白拿性能）

- 内置 ORT 1.17.1 支持 **NNAPI EP**：`new SessionOptions().addNnapi()` 一行即可把算子
  调度到 GPU/NPU，GAN 类卷积网络通常 2~5 倍提速；必须 try-catch 回退 CPU
  （部分算子 NNAPI 不支持会回退，极端情况可能更慢或崩溃）。
- 更进一步换 NCNN/MNN 框架可再省体积提速，但要加 C++ so 与模型转换工具链，
  对现有构建链改造大，性价比低。

## 四、落地建议（按性价比排序，均未验证）

1. **白捡的风格扩充**（可行性最高）：官方 AnimeGANv3 releases /
   Portrait_Inference 仓库有 Disney、USA cartoon、Kpop、Comic、Cute、8bit、
   Nordic myth 等现成人像 ONNX。`fixFaces` 管线原样复用，每加一个风格只是
   多一个 session + 一个入口。建议先挑 Disney / USA / Kpop 三个试效果。
   - ⚠️ 各模型输入归一化（/127.5-1 vs /255）、布局（NHWC/NCHW）可能不同，需逐个核对
2. **加 AnimeGANv2 face_paint_512_v2** 作为第二档人像风格（约 8.6MB ONNX），
   厚涂感与 Ghibli 差异明显，社区验证最充分。
3. **开 NNAPI 加速**：一行配置 + 回退逻辑。多脸合影场景（8 张脸 × 每脸 4~12 秒）
   收益最大；风险是个别机型 NNAPI 崩溃，务必留 CPU 回退和灰度开关。
4. （可选）White-box Cartoonization 补一个"通用卡通"整图风格，与人像风格互补。
5. **不做端侧 SD**。
6. 包体优化线索：parsenet 占资产一半（21.6MB/41.8MB），可考虑改为首次使用时下载
   或换更小的脸部分割模型（未验证替代品）。
7. **License 注意**：AnimeGANv3 官方 license 为**非商业**（商用需联系作者授权）；
   个人自用无碍，若日后上架收费需先解决授权。
