# 01 · 明亮度/清晰度调查（2026-09-20）

> 用户原始问题："这个 APP 拼豆算法是不是不太好？我感觉没有别的明亮和清晰，是我的错觉吗？"
> 结论：**不是错觉**，三个可量化的技术成因 + 一个观感成因。当日未改代码。

## 管线现状（PatternEngine.java）

`generate()` 五步：

1. **居中裁剪**到画幅比例
2. **源图压到长边 ≤1024**（Bitmap.createScaledBitmap）
3. **工作网格重采样**（默认 `boxResample`；"清晰轮廓"开走 `dominantResample`；去背景开走 `gridWithBackground`）
4. **画面调节**（亮度/对比/饱和，默认全 0）
5. **最近豆色匹配**（Lab 欧氏；"精准配色"开才 CIEDE2000）→ 可选 FS 抖动（Lab 空间）→ 展开 b×b → 形状裁切 → 杂色清理（默认关）→ 限色合并（默认不限）→ 统计

## 变暗的量化成因（probes/pindou_algo_probe.py）

模拟照片色分布（L* 30~92、C* 8~70 随机），复刻 App 参数：

| 实验 | 结果 |
|---|---|
| ① 色板匹配（N=8000） | 全体平均 L* **-0.74**、C* **-3.75**（变灰）；**L\* 70~92 段平均 -5.20**；L\* 30~50 段 +2.83；26.5% 样本 L* 掉超 6 |
| ② 伽马均值（N=8000） | sRGB 空间均值比线性光均值 **L\* -4.26**（更暗）、C* +1.53 |
| ③ 覆盖度 | 随机照片色到 90 色板最近豆：中位 ΔE **13.8**、P90 **26.0** |
| ④ 色板分布 | 90 板平均 L* 57.9 / C* 40.1；模拟照片平均 L* 61.2 |

解读：

1. **`boxResample`（PatternEngine.java:1060）直接对 0-255 像素求均值 = 伽马空间混合光线**。正确做法是先 sRGB→线性光、平均、再编码回来。对亮部（天空/高光/浅背景）差异最大——单这一项整图暗一档。开源对标 Pindo（400★）的 downscaler.ts 明确做了这个校正。
2. **色板匹配把亮区拉暗**：L* 70~92 恰是天空/肤色/白色物体等照片主体所在区间，因为 90 色板里"亮且饱和"的豆色少。
3. **无自动增强**：全工程搜不到直方图拉伸/自动饱和/锐化（findstr 确认）；竞品普遍默认"一键美化"。

## 变糊的量化成因

1. **默认 58×58**：4000px 长边照片每颗豆吞约 70×70 源像素，同类产品默认偏小。
2. **dither=false**：无抖动的渐变区域糊成大片平色块（"糊感"主因）。
3. **dominant=false**：边界灰毛边无解（注释原文"消颜色边界的灰色毛边"，PatternEngine.java:941）。
4. ΔE 中位 13.8 的色板覆盖度是拼豆物理限制（所有 App 共有），竞品靠抖动+增强撑观感。

## 观感成因（与算法无关但影响"看起来亮不亮"）

生成后默认视图是**效果图模式**（PatternView.java:36 `mode = MODE_EFFECT`）：每豆画成 r=0.46·cell 圆 + `darken(rgb, 0.72)` 深色描边圈（:856-862），坐在米色底板上留缝隙；图纸页的满格平铺画法（:1002）非默认。同一张图纸，圆豆渲染天生比竞品常用的满格色块更暗更软。

## 第一轮修复优先级（后被第二轮"先配后投"方案部分取代，以 README 路线为准）

- P1 boxResample 改线性光平均（全局提亮 ~4 L*）
- P1 匹配前亮端补偿（或默认饱和度 +10）
- P2 抖动默认开或"平滑/细节"档；建议尺寸默认 80
- P2 效果图模式减淡描边 / 加平铺预览开关
- P3 CIEDE2000 默认开
